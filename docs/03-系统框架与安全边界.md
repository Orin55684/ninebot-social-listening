# 系统框架与安全边界

版本：0.1  
状态：概念方案

## 总体原则

第一期采用轻量的模块化单体结构。正式服务器负责数据同步、规则处理、业务接口、页面和任务调度；公司本地模型由独立推理服务提供。系统通过模型适配层调用该服务，不将模型绑定到 Cherry Studio、WorkBuddy 或某个固定供应商。

## 逻辑链路

```text
微伴助手历史与增量消息
          │
          ▼
数据接入与同步状态管理 ───── VOC或社媒预留接口
          │
          ▼
标准化 去重 脱敏 稳定匿名ID
          │
          ▼
轻量规则筛选与上下文组装
          │
          ▼
公司本地模型适配层 ───── 公司私有模型服务
          │
          ▼
问题分类 事件聚合 风险评分 摘要
          │
          ├──── 日报 周报 月报
          │
          ▼
售后人工确认 ───── 飞书告警
          │
          ▼
最终分类 风险等级 处理结论 误报原因回流
```

## 模块边界

| 模块 | 责任 | 不承担的责任 |
| --- | --- | --- |
| 数据接入 | 调用微伴助手或未来VOC接口，保证增量位置、去重和失败重试 | 不做业务判断 |
| 数据治理 | 字段统一、敏感信息处理、匿名ID和访问控制 | 不改变原始业务含义 |
| 分析编排 | 规则筛选、上下文组装、调用模型、结构化结果校验 | 不直接决定最终风险等级 |
| 事件中心 | 相似反馈聚合、趋势计算、事件状态和证据关联 | 不自动对外处置 |
| 预警 | 依据规则生成候选，支持人工确认和飞书通知 | 不替代售后团队升级决策 |
| 报告 | 生成日级热点及周月洞察 | 不自动发布到外部渠道 |
| 反馈与评估 | 保存人工结论、误报原因和评估数据 | 一期不自动训练或微调模型 |

## Codex与生产模型的职责边界

- Codex可用于整理需求、设计结构、生成和维护项目代码、编写测试及协助排障。
- Codex不接收生产群聊内容，也不参与正式运行时的消息分类、摘要或风险判断。
- 正式运行时的模型调用只经过公司内网可访问且获批准的模型接口。
- 在公司接口就绪前，DeepSeek 适配器仅用于模拟或公开数据，并在网络调用前执行数据分类拦截。
- 生产系统不依赖 Codex 会话持续在线。
- 由 Codex 生成的代码仍需经过人工审查、凭证配置、安全检查和部署验收。

## 2核2GB服务器上的部署边界

该服务器适合作为轻量应用节点，但不适合运行大语言模型。概念上可承载数据同步、任务调度、接口、简单页面和小规模数据库访问；以下能力需要谨慎控制：

- 不在本机加载大模型或大型向量模型。
- 不建设 Kafka、Elasticsearch 等高维护成本组件。
- 限制并发任务数，使用分批处理和背压，避免模型服务变慢时耗尽内存。
- 日志设置轮转与保留上限。
- 半年历史数据、索引和备份的实际空间必须经过抽样测算。
- 若文本和索引接近磁盘安全线，应扩容云硬盘或将冷数据归档到公司批准的存储位置。

## 安全分区

### 原始数据区

保存从数据源取得的原始字段，访问权限最严格。原文仅在人工核验确有必要时展示。

### 分析数据区

保存脱敏文字、匿名身份、分类、事件和统计结果。公司模型只能接收完成敏感信息处理且业务所需的最小上下文。

### 输出区

保存摘要、趋势、告警和周期报告。飞书消息默认不附带大量群聊原文，只提供最少证据和受控查看入口。

## 社媒与VOC预留接口

在 VOC 导出能力明确前，不实现具体连接器。接口设计需允许后续导入来源平台、内容标识、发布时间、作者匿名标识、文字、互动量、链接、分类、风险及事件关联字段。社群模块不得依赖社媒数据才能工作。

## 仍需验证的技术假设

- Cherry Studio 或 WorkBuddy 中的公司模型账号是否同时具备服务端 API 权限。
- 公司模型是否支持稳定的结构化 JSON 输出。
- 模型服务的网络位置、限流、并发和日志策略。
- 使用同一标注样本比较 DeepSeek 开发结果与公司私有模型结果的方法。
- 微伴助手增量接口在高消息量下的延迟和分页行为。
- 飞书通知是否允许使用机器人，以及能否携带受控系统链接。
- 2 核 2 GB 服务器在真实数据规模下的数据库与任务并发上限。
